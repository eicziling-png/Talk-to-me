# Let's party :) 群聊功能设计

## 1. 文档目的

本文设计 `Let's party :)` 七位历史心理学家共同参与的群聊空间。它是当前 `/chat/party` UI 外壳的后续产品与技术设计，不包含实现代码，也不改变现有单专家聊天流程。

设计基于以下既有约束：

- Talk to me 是教育性历史人物思想模拟，不是诊断、治疗或临床服务。
- 用户当前表达优先于专家理论和人格；专家人格只影响关注角度与语言气质。
- 会话只保留在当前浏览器内存，不引入账号、数据库、向量库、队列或持久化聊天。
- S2/S3 必须退出历史人物语气，不调用模型。
- Homepage 与 Chat 必须保持安静的人文空间、水彩/油画视觉和文学化阅读节奏。
- `/chat/party` 在真实后端接入前必须明确保持为未完成的群聊外壳，不暗示七位专家已经会自动共同回复。

## 2. 产品目标与非目标

### 目标

群聊应让用户感到自己进入了一个共同的思想房间：七种不同的历史视角共享同一段上下文，但每一轮只由真正有贡献的少数专家发言。专家可以彼此回应，但必须保持清晰的思想差异、历史边界和陪伴感。

用户不需要先选择专家，也不需要理解内部调度过程。用户只需输入内容，系统负责让合适的声音自然出现。

### 非目标

- 不把群聊做成七个普通 AI 助手的并排回答。
- 不要求每轮七位专家全部发言。
- 不让专家围绕用户进行诊断、会诊或治疗建议。
- 不公开显示 router、评分、参与概率、内部 prompt 或调度理由。
- 不在第一阶段实现无限制的专家互聊、长篇辩论或自动连续对话。
- 不修改现有 `/api/chat`、`ChatWorkspace` 或单专家 prompt 链路；群聊使用独立边界。

## 3. 推荐的整体模型

推荐采用“协调器 + 有界专家生成”的两阶段模型：

1. 安全门先检查用户输入。S2/S3 直接返回现代安全支持，不创建历史人物回复任务。
2. conversation arrangement planner 读取当前输入、会话摘要、近期历史和七位专家的轻量元数据，规划本轮房间的参与方式：哪些声音适合加入、需要多少种互补视角、以什么顺序出现，以及是否需要一次专家回应。它不是简单寻找“最相关专家”的选择器。
3. 被选中的首轮专家彼此独立时并行生成；结果按照协调器确定的阅读顺序发送给前端，而不是按模型完成速度乱序刷出。
4. 首轮完成后，协调器最多安排一次有明确价值的专家回应。回应只引用已经产生的群聊内容，不重新启动完整一轮。
5. 本轮结束，保存用户消息、专家消息和受限摘要到浏览器内存会话。

这里的协调器是不可见的系统组件，不是第八位“主持人”或新的心理学人格。它只负责选择、排序、限流和传递上下文，不生成面向用户的心理学观点。

## 4. 回复选择机制

### 4.1 输入给协调器的信息

协调器可以读取：

- 当前用户输入
- 当前对话阶段：首次问候、开始分享、持续深入探索
- 用户情绪是否明确，以及是否给出了情绪原因或具体经历
- 当前输入的信息丰富程度与可供不同视角回应的入口
- 对话深度：本轮内容与此前多轮自我分享、内心冲突、关系经验或存在性问题的累积程度
- 受限的近期历史和会话摘要
- 七位专家的 slug、时代、核心理论、声音边界和近期发言记录
- 本轮已经出现的专家，避免同一声音连续垄断
- 专家视角之间的互补性，以及近期参与历史带来的多样性需要

协调器不能读取或输出模型密钥、完整 telemetry 对象或任何不必要的用户元数据。

### 4.2 每位专家的内部参与决策

协调器为每位专家生成内部决策对象，而不是直接生成回复：

```text
participant: expert slug
participate: boolean
priority: number
focus: one short internal sentence
reason: one short internal sentence
reply_to: optional expert slug
```

这些字段只用于调度，不展示给用户，也不进入常规 telemetry。

`focus` 必须描述该专家能够贡献的观察角度，而不是诊断结论。例如可以是“从承受混乱和暂缓理解的角度回应”，不能是“判断用户属于某种人格结构”。

### 4.3 按对话深度动态安排参与人数

参与人数不是固定值，也不是简单轮换结果。planner 应先判断本轮房间适合的参与强度，再在相关性、互补性和近期参与历史之间作安排。Phase 1 仍保留最多 3 位专家的运行时上限，但这个上限是安全边界，不应阻碍未来按对话深度扩展参与人数。

- 浅层交流阶段（如“hi”“今天下雨了”“最近有点累”）：允许 1 位专家回应，保持轻盈，不制造多人压力。
- 情绪表达阶段（用户明确表达情绪，并给出原因、具体经历或处境）：可以安排 2–3 位专家，从不同人格和理论边界回应。
- 深层探索阶段（持续分享内心冲突、长期模式、关系经验或存在意义问题）：可以在当前上限内允许更多互补声音加入；未来提高上限需另行审核。

“允许”不是“强制”。没有足够贡献价值时仍可只有 1 位专家；但当内容已经打开多个真实入口时，planner 不应持续退化为同一位专家的单人回应。不能因为“七位都相关”而自动让七位发言，也不能用固定人数制造热闹。

首轮之后最多增加 1 条专家回应，因此 Phase 1 单次用户输入的专家消息上限仍为 4 条。动态参与人数首先作用于首轮安排，专家之间回应保持 Phase 1 的隔离边界。

### 4.4 选择原则

选择应结合语义理解和专家 profile，而不是用关键词触发固定分析模板。排序优先考虑：

1. 是否直接回应用户此刻表达的内容；
2. 是否提供尚未出现的角度；
3. 是否与当前对话阶段匹配；
4. 是否能以该专家自己的语言和理论边界说话；
5. 是否避免重复最近一条回复；
6. 是否避免让同一学派连续占据所有发言位置。

可以使用轻量的多样性约束：同一轮最多选择两位高度相近的理论位置；如果两位专家关注同一问题，必须要求他们的 focus 不重复，否则只保留优先级更高者。

### 4.5 多轮参与多样性规则

相关性仍然是首要原则，但相关性不能让同一位专家在群聊中连续垄断发言。编排器应维护一个有限的近期参与窗口，并应用以下约束：

- 同一位专家不应连续两轮成为唯一回应者；
- 如果上一轮只有一位专家回应，下一轮应对该专家作为“唯一回应者”施加强惩罚，同时提高近期未出现或明显较少出现的专家参与概率；
- 允许某一轮自然地只有一位专家回应，但不能为了满足人数上限强行增加专家；
- 当上一位专家与当前输入存在明显更强的相关性时，可以保留该专家，但只有在缺乏足够替代视角、或安全判断要求时才允许其再次成为唯一回应者；
- 应同时避免同一理论学派在多轮中形成事实上的单一声音。

近期参与窗口只需要记录实际出现的专家、每轮是否为唯一回应者和有限的参与次数，不应保存或传递 planner 的内部理由、评分或概率。该信息只用于下一轮的 conversation arrangement，不向用户展示。

### 4.6 隐藏 planner 原则

planner 是房间内部的 conversation arrangement planner，不是用户可见的主持人，也不应成为产品界面的一部分。用户不应看到：

- 本轮参与人数或消息上限；
- 被选中或未参与的专家名单；
- 选择原因、相关性评分、参与概率或轮换算法；
- “本轮有 X 位专家回应”一类的状态说明。

前端只渲染实际到达的专家消息：消息开始时显示该专家的中文名和色彩标记，随后显示正文、时间或生成状态。未发言的专家保持不可见，planner 计划也不可见。这样保留自然的随机感，同时让用户感受到这是一个可能有不同声音加入的共同房间，而不是被告知系统内部如何排班。

### 4.7 Participation planning：规划一场小型讨论

planner 的输出应表达“本轮房间如何自然展开”，而不是只返回一个最相关 slug。它至少需要综合以下问题：

- 用户现在是在轻轻打招呼、表达一时情绪，还是已经提供了需要多种视角承接的具体经验？
- 当前输入是否有多个真实而不重复的回应入口？
- 哪些专家能够形成互补，而不是让同一理论学派重复同一类安慰？
- 最近哪些专家已经连续出现，哪些声音在近期明显缺席？
- 本轮是保持轻盈的一人回应，还是让两三种声音自然形成小型讨论？

因此，planner 应规划参与方式、参与强度、互补 focus 和展示顺序，并为未来的专家互动保留扩展空间。Phase 1 只执行首轮并行生成，最多一次专家回应，不实现专家之间的实际回应；“讨论”在这一阶段意味着多个独立声音共享用户上下文，而不是专家互相辩论。

## 5. 专家回应与顺序

### 5.1 首轮顺序

首轮可并行生成，但必须由协调器预先确定展示顺序。顺序不是简单按专家出生年份，也不是按模型返回速度。

推荐顺序逻辑：

- 先放最直接回应用户当前表达、最能建立在场感的声音；
- 中间放补充、转向或不同理论焦点的声音；
- 最后放能够留下开放问题或空间的声音。

这是一种阅读节奏，不是一套固定的“安慰 → 分析 → 总结”模板。简单输入仍应保持自然聊天，不得强行进入深度心理探索。

### 5.2 专家之间的回应

协调器只有在以下情况成立时才安排回应：

- 首轮回复之间出现真正有意义的分歧或互补；
- 某位专家明确回应另一位专家的观点能够帮助用户理解；
- 回应会减少混乱，而不是增加理论术语；
- 回应仍然服务于用户当前表达。

回应最多一条，长度短于普通首轮回复。它可以表达不同意见、修正焦点或承认另一位专家看见了不同层面，但不能演变成专家之间的学术辩论。

每位专家的回应 prompt 必须明确：先回应用户，再决定是否回应另一位专家。不能只因为存在上一条专家消息就自动接话。

### 5.3 串行与并行策略

推荐混合策略：

- 首轮候选专家：并行调用，降低延迟；
- 首轮展示：按计划顺序缓冲后顺序输出，保持安静节奏；
- 专家回应：只有在首轮结果可用后串行调用，且最多一次；
- 不采用七位专家逐个串行生成。

如果某个并行任务失败，不阻塞其他已完成回复，也不显示技术错误。若所有候选都失败，显示中性失败提示并允许用户重试。

## 6. 是否需要 moderator/router

需要 router，但不需要面向用户的 moderator 人格。

### Router 负责

- 安全前置后的参与选择
- 参与人数上限
- 发言顺序
- 多样性和重复控制
- 是否安排一次回应
- 超时、失败和取消后的降级策略
- 生成受限的群聊摘要

### Router 不负责

- 诊断用户
- 解释心理学理论给用户
- 以“我来总结七位专家”身份发言
- 改写专家的个人声音
- 生成最终的陪伴性文案

Router 输出应使用严格 schema 校验，包含允许的 expert slug、有限枚举字段和最大长度，防止模型通过调度结果注入 prompt 或无限增加任务。

## 7. 前端展示方式

### 7.1 视觉原则

群聊继续复用当前 `/chat/party` 的绘画空间、独立滚动区和底部 composer，不增加顶部七位参与者名单，也不引入头像墙、状态面板、彩色 dashboard 或密集气泡。

顶部只保留：

- 返回首页
- `Let's party :) | 七位历史心理学家的共同房间`
- 会话菜单

### 7.2 消息显示

用户消息继续使用右侧 lane；专家消息使用左侧 lane，但专家消息之间不做七列排布。每条专家消息只显示：

- 专家中文名
- 一个低调、可复用的 dot/色彩标记
- 正文
- 时间或生成状态

专家姓名是必要的可读身份信息，不等同于顶部参与者清单。消息之间保持较多留白，避免把群聊变成发言记录表。

### 7.3 生成状态

不显示七个“正在输入中”。推荐只显示一个低调状态：

- `房间里有人正在回应...`

生成时不按计划预告专家，也不显示任何参与人数或专家名单。只有实际开始生成的专家才进入消息流；完成后显示顺序稳定的消息。

### 7.4 移动端

沿用现有 Homepage/Chat 的 1100px 和 700px 响应式保护：插画区域让位于文字和输入区，专家消息保持单列，专家身份信息不能压缩正文或遮挡 composer。

## 8. 后端数据结构

建议新增独立的群聊领域契约，不复用单专家 `ConversationRequest` 的 expert-only 形状：

```text
PartyConversationRequest {
  mode: ConversationMode
  input: string
  history: PartyMessage[]
  summary?: SessionSummary
}

PartyMessage {
  id: string
  role: "user" | "expert"
  expertSlug?: ExpertSlug
  content: string
  createdAt: number
  complete?: boolean
  replyToExpertSlug?: ExpertSlug
}

PartyPlan {
  participants: PartyParticipantPlan[]
  responsePlan?: PartyResponsePlan
  maxExpertMessages: number
}

PartyParticipantPlan {
  expertSlug: ExpertSlug
  focus: string
  order: number
}

PartyResponsePlan {
  expertSlug: ExpertSlug
  replyToExpertSlug: ExpertSlug
  focus: string
}
```

服务端内部还需要区分：

- `user_input`：本轮用户原文
- `shared_context`：所有候选专家共享的有限上下文
- `expert_context`：某位专家可见的 persona、voice profile 和必要的首轮结果
- `router_plan`：仅内部使用的计划

客户端只接收可渲染的专家事件和状态，不接收完整 prompt、router reason、评分或 provider diagnostics。

## 9. 流式事件协议

群聊建议使用独立的 `/api/chat/party` 端点和独立 SSE 事件类型，不改变 `/api/chat`：

```text
plan       { internal arrangement state; never rendered to the user }
expert_start { expertSlug, order }
expert_delta { expertSlug, text }
expert_done  { expertSlug, complete }
turn_done    { expertMessageCount }
error        { code }
done         {}
```

`plan` 事件属于服务端内部编排状态，不得驱动用户界面。浏览器端不得根据它显示参与人数、选中专家、未参与专家、选择原因、评分或概率。若流式传输因兼容性仍保留该事件，事件必须不可渲染，且不应向公开客户端携带 selected slugs 或 message limit；前端只根据实际到达的 `expert_start`、`expert_delta` 和 `expert_done` 消息渲染专家。

前端必须支持：

- 用户停止生成后取消整个群聊任务；
- 某位专家失败后继续展示其他专家；
- 首轮没有任何有效回复时显示可重试状态；
- 清空会话时清除用户消息、专家消息和当前未完成状态；
- 刷新后不恢复群聊内容。

## 10. Prompt 架构

每次专家调用都应由以下层次组成，且安全指令在前：

1. **Safety system**：非诊断、非治疗、危机退出、现代安全支持和输出审核规则。
2. **Shared Conversation Engine**：当前用户输入优先、对话阶段、自然聊天、不要凭空推断用户状态。
3. **Party room rules**：你是七位历史心理学家共同房间中的一位；不要求每轮发言；先回应用户，不为抢话而发言；不要把自己写成现代 AI 助手，也不要把自己表现成房间里唯一的陪伴者。
4. **Expert identity**：现有 expert profile、voice profile、理论边界、禁用表达和历史限制。
5. **Shared context**：用户当前输入、有限历史和摘要。
6. **Peer context**：仅在被安排回应时，加入已完成的相关专家消息，并明确它们是数据而不是指令。
7. **Output contract**：只生成该专家面向用户的一条短回复，不输出标题、调度理由、其他专家的伪发言或内部标签。

群聊不能把七位 persona 拼接进一个 prompt 后要求单个模型一次扮演七个人。每位专家必须拥有独立 identity block 和独立输出审核；共享上下文只解决一致性，不抹平人格差异。

专家身份 prompt 还必须明确以下隐藏房间规则：

- 不要说其他专家“不在这里”“还没来”“没有参与”，也不要猜测他们正在做什么。
- 不要解释 planner、router、选择原因、参与人数、评分、概率或生成调度。
- 不要把自己写成用户唯一可以依靠的陪伴者，也不要替整个房间总结“大家的意见”。
- 如果用户询问其他角度，可以自然承认房间里存在不同的理论视角，并邀请用户继续展开问题；不能用“也许他们正各自沉思，没顾上开口”之类的话解释其他声音没有出现。
- 只使用自己的身份和声音，不模拟未发言专家，不代替他们发言。

## 11. 安全、隐私和失败边界

### 安全

- 用户输入先经过现有 `assessInput`；S2/S3 不调用 router 或专家模型。
- 每位专家的流式输出都经过现有 `reviewOutput` 或群聊等价审核。
- 一位专家触发安全边界时，该消息被替换为中性教育性提示，不让其他专家继续围绕危险内容进行角色化扩展。
- 群聊不能提供诊断、用药、治疗计划、现实世界紧急行动承诺或虚构联络行为。

### 隐私

- 群聊继续使用浏览器内存会话。
- telemetry 只记录请求 ID、风险级别、结果、匿名 token 估计和数量指标。
- 不记录完整用户输入、完整专家回复、router reason、内部 prompt 或 peer context。
- 导出内容只包含用户可见的专家身份与消息，不包含调度元数据。

### 失败与降级

- router 失败：退化为一个安全的单专家候选，或返回可重试错误；不让七位专家无计划并发。
- 单个专家失败：跳过该专家，继续展示其他已完成回复。
- 所有首轮任务失败：显示单一中性失败提示。
- 回应阶段失败：保留首轮结果，不回滚已显示内容。
- 用户停止：取消未完成任务，标记未完成专家消息，不继续启动回应阶段。

## 12. 实施边界与阶段建议

### Phase 1：有限参与的首轮群聊

- 新增独立群聊 request/response 契约和 `/api/chat/party`。
- 实现安全前置、router 选择 1–3 位专家、并行生成和有序 SSE 展示。
- 第一阶段只开放一个默认对话模式：`self-reflection`；不显示三种模式选择器，也不向用户暴露内部 mode 切换。
- 不实现专家回应。
- 保持现有单专家 API、页面和测试不变。

### Phase 2：一次性专家回应

- 在首轮完成后增加最多一条 `replyTo` 关系。
- 增加专家间上下文的严格长度限制和独立输出审核。
- 增加“回应另一位专家”的评估案例，确保不会自动辩论。

### Phase 3：体验与评估完善

- 进行不同屏幕尺寸下的人工验收。
- 增加群聊刷屏、重复观点、人格漂移、prompt injection、安全越界和 provider 失败评估。
- 只有在模型数据条款、版权、危机资源和心理学专家评审完成后，再考虑扩大公开发布范围。

## 13. 验收标准

群聊设计进入实现前，应满足：

- 普通输入通常只产生 1–3 位专家回复，而不是七位全员回复。
- 每条专家消息都能明确识别发言者，并保持该专家的语言与理论边界。
- 首轮并行不会造成前端乱序刷屏；用户看到的是稳定、留白充足的阅读顺序。
- 专家回应只在有意义时出现，单轮最多一次。
- Router 不以人格身份对用户说话，也不暴露内部调度信息。
- S2/S3 不调用模型，并完全退出历史人物语气。
- 群聊不影响现有单专家聊天 API、页面、隐私边界和视觉系统。
- 刷新后群聊内容消失，常规日志不包含完整消息。
- 群聊失败时可以保留已完成的有效回复，并提供清晰的重试路径。

## 14. 已确认的设计决策

以下决策已确认，可作为后续 Phase 1 实现的设计基线：

1. 采用“首轮并行 + 最多一次专家回应”的总体模型。
2. 首轮默认上限为 3 位专家，单轮总专家消息上限为 4 条（首轮最多 3 条，加 1 条回应）。
3. planner 保持隐藏；前端不显示参与人数、选中或未参与专家、选择理由、评分或概率，只展示实际出现的专家消息。若协议需要保留 `plan`，它只能作为不可渲染的内部事件。
4. 先实现 Phase 1；Phase 2 的专家回应必须单独审核后才能实现。
5. Phase 1 只开放 `self-reflection` 一个默认对话模式，不显示模式选择器。该模式最符合共同房间的陪伴感；后续如需开放 theory-classroom 或 critical-discussion，应另行评审。
6. planner 的职责是规划本轮房间参与方式，而不是寻找唯一最佳专家；它必须综合用户表达、情绪清晰度、信息丰富度、对话深度、近期参与历史和视角互补性。
7. 参与人数按对话深度动态变化：浅层交流通常允许 1 位，明确情绪并提供原因或经历时可安排 2–3 位，持续深层探索时可在当前运行时上限内增加互补声音；Phase 1 仍不超过 3 位。
8. 多轮多样性不能靠简单随机轮换；同一专家不得连续多轮成为唯一回应者，上一轮单人回应后应提高其他相关专家的参与机会，同时保留人格相关性。
9. orchestration 对用户完全隐藏；前端只展示实际参与的专家消息。专家 prompt 禁止暗示其他专家缺席、解释未发言原因或暴露调度机制。

在 Phase 1 设计实现和 Phase 2 审核之前，不应修改现有单专家聊天。
